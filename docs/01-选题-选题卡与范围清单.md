## 二、硬性淘汰条件检查

| # | 淘汰条件 | 判定 | 说明 |
| ---: | --- | --- | --- |
| 1 | 无法说明具体目标用户和使用场景 | 未触发 | 三类用户明确；场景细节待真实调研补充 |
| 2 | 无法形成可演示的核心业务闭环 | 未触发 | 报修→派单→处理→验收/返修闭环完整 |
| 3 | 关键数据、硬件、收费接口或第三方服务无法获得 | 未触发（有条件） | 全部数据可自建/模拟。前提：不依赖统一身份认证、短信网关、支付接口 |
| 4 | 核心范围明显超出项目周期和个人能力 | 未触发（有条件） | 前提：首版限定一个宿舍片区、5 个必做模块 |
| 5 | 项目主体只是调用外部 API 或套一个聊天窗口 | 未触发 | 主体是工单状态流转与业务规则 |
| 6 | 依赖真实支付、复杂即时通信、大规模并发、多租户或跨校数据共享 | 未触发（有条件） | 前提：以上均列入"本期不做" |
| 7 | 涉及难以控制的隐私、医疗诊断、金融交易或其他合规风险 | 未触发（有条件） | 报修图片可能含宿舍内部与个人信息，需权限隔离、脱敏演示样例、自愿授权 |
| 8 | 依赖难以获得的硬件或设备 | 未触发 | 无需摄像头、门禁、IoT 设备 |

**结论**：无硬性淘汰项，**有条件推荐立项**。成立条件为第 3、4、6、7 项的"前提"全部满足，且真实调研不推翻核心闭环。

## 四、范围控制（四级功能清单）

### 4.1 必做（5 项，缺一不可形成闭环）

| # | 模块 | 关键规则与预期结果 | 主要角色 |
| ---: | --- | --- | --- |
| M1 | 宿舍与维修范围配置 | 维护楼栋、楼层、房间、故障类别；维护维修人员与其负责的类别/楼栋范围；删除已被工单引用的基础数据须拦截或转为停用 | 宿管 |
| M2 | 报修受理 | 学生填写地点、故障类别、描述并上传图片；可查历史工单；**同一房间存在未结同类报修时给出提示并阻止或要求确认**，避免重复派单 | 学生 |
| M3 | 派单与改派 | 按故障类别＋负责范围推荐并指派维修人员；记录接单、退单、改派及理由；退单后工单回到待派单状态，不得停留在中间态 | 宿管、维修人员 |
| M4 | 维修与验收 | 维修人员提交处理说明与结果；学生确认完成或提出返修；**每次处理独立留痕，返修生成新一轮处理记录且不覆盖历史**；仅当前受理人可操作对应环节 | 维修人员、学生 |
| M5 | 工单统计 | 按楼栋、故障类别、时间区间统计工单量、平均处理时长、返修次数/返修率；统计口径与状态定义一致 | 宿管 |

### 4.2 应做（保证系统基本完整）

1. 登录与会话管理，学生/宿管/维修人员三类角色的菜单与数据可见范围隔离。
2. 工单列表的查询与筛选（状态、楼栋、类别、时间、我的工单）。
3. 状态变更日志：记录操作人、时间、前后状态与备注，供追溯与答辩演示。
4. 报修图片上传、存储与按权限查看；文件类型、大小校验与失败提示。
5. 初始化/演示数据脚本：楼栋房间、故障类别、维修人员、若干处于不同状态的工单。
6. 统一异常处理与表单校验：必填项、越权访问、非法状态跳转、重复提交、图片上传失败均有明确提示与可恢复路径。

### 4.3 选做（核心版本跑通后再加，按此顺序）

1. 站内消息/邮件提醒（新工单、派单、待验收）。
2. 统计结果可视化图表（趋势、类别占比）。
3. 重复报修提示的规则优化（时间窗口、类别相似度）。
4. 移动端页面适配，方便学生在宿舍现场提交。

### 4.4 本期不做（主动排除）

1. 在线支付、维修收费、材料计费。
2. 即时聊天、语音通话、复杂消息推送。
3. 对接学校统一身份认证（CAS/OAuth）、短信网关、既有后勤系统数据同步。
4. 跨校区、多学校、多租户与大规模并发。
5. AI 故障自动诊断、智能派单算法、图像识别定损。
6. 地图定位、门禁/IoT 设备对接、人脸识别。

> **降级逻辑**：任一选做项或外部依赖受阻时，不影响 4.1 必做闭环可运行、可演示。图片上传失败时允许先提交文字报修并给出补传入口；消息提醒不可用时由系统内工单状态与列表承担查询职责；统计模块异常不影响工单流转。

## 五、验收方案

### 5.1 端到端主流程（答辩演示）

学生 A 在 3 栋 502 提交"水龙头漏水"报修并上传图片 → 宿管受理，系统按类别与负责范围推荐维修人员 B 并派单 → B 接单、上门、提交处理说明与结果 → 学生 A 确认验收 → 工单归档 → 宿管在统计页看到该工单的处理时长计入。

### 5.2 异常与边界场景（至少 2 个，建议全部覆盖）

| # | 场景 | 期望结果 |
| ---: | --- | --- |
| E1 | 维修人员接单后退单，宿管改派给另一人 | 工单回到待派单，退单理由留痕，改派后仅新受理人可处理，不产生两条并行处理记录 |
| E2 | 学生提出返修 | 工单回到处理中，生成新一轮处理记录，历史处理记录与验收意见完整保留，返修次数计入统计 |
| E3 | 同一房间已存在未结同类报修时再次提交 | 给出明确提示并阻止重复派单（或要求学生确认后关联原工单） |
| E4 | 越权与非法状态跳转（学生执行派单、维修人员自行确认验收、对已归档工单重复验收） | 全部拦截并返回可读提示，状态与数据不被破坏 |
| E5 | 报修图片上传失败 / 文件类型不合法 | 给出明确失败原因，允许文字报修先提交并在后续补传（降级路径） |

### 5.3 交付物清单

1. 可独立运行的系统源代码与运行环境说明（依赖、版本、启动命令）。
2. 初始化/演示数据与部署说明。
3. 测试记录：覆盖 5.1 主流程与 5.2 各场景的操作步骤、预期与实际结果。
4. 数据库设计与工单状态流转说明（供答辩解释核心设计）。
5. 论文及后续阶段材料按 README 的阶段-技能对照表沉淀到仓库。

## 六、生成《毕业设计任务书》前需补齐的信息

任务书初稿在下列信息明确后再生成，避免产出"看似完整"的空壳文档：

1. **真实流程核实结论**：本校宿舍报修目前走什么渠道？由谁派单？是否需要学生签字验收？是否有返修环节？→ 决定角色与状态机。
2. **技术基础与约束**：已掌握的框架/数据库、是否指定必须使用某技术栈、毕设剩余时间与开题/中期/答辩节点日期。
3. **数据与范围确认**：能否获得楼栋房间、故障类别等基础数据（或同意合理模拟）；是否同意首版限定一个宿舍片区；是否需要加入 AI 能力（本题不加 AI 更稳）。
4. **模板信息**：当届任务书模板、学院/专业、学生姓名、指导教师、下达时间。

补齐后按 `topic-selection` 第七步生成任务书初稿，交指导教师核对题目、任务范围与进度后再下达；确认后使用 `proposal-defense` 撰写开题报告。
