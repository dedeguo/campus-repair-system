# 阶段一 · 选题卡与范围清单

**拟定题目**　高校宿舍报修与维修工单管理系统设计与实现
**题库编号**　03　|　**难度**　L2 标准业务闭环 ＋ 1 项 AI 增强（按 L3 的 AI 验收要求执行）　|　**完成方式**　一人一题，独立完成
**技术栈**　JDK 21 ＋ Spring Boot 3.5.x ＋ MySQL 8.0 ＋ Vue 3.5.x（Node 22 LTS）；AI 能力走后端代理，可离线 Mock
**更新**　2026-11-08（v3：填入行政信息、确定主流版本、简化流程状态）　|　**状态**　信息已齐备，待指导教师审核

> **证据边界**：文中"现有报修流程"来自学生本人说明（校内报修系统 ＋ 电话沟通），本系统为**模拟实现**，不与校内真实系统对接；楼栋房间、故障类别、维修人员、学生账号均为**模拟数据**。
> 不得把模拟数据写成真实调研结果，不得虚构问卷、访谈、用户数量、"调查显示"或处理效率提升比例。

## 一、选题卡

| 检查项 | 内容 |
| --- | --- |
| 项目名称 | 高校宿舍报修与维修工单管理系统 |
| 目标用户 | ① 在校住宿学生（报修、验收、返修）；② 宿管/后勤受理员（受理、派单、改派、统计、基础数据配置）；③ 维修人员（接单、退单、提交处理结果）。管理员权限并入宿管角色，不单列第四类角色。 |

| 必做功能 | 见第六节 M1～M6（5 个业务模块 ＋ 1 项 AI 增强），构成核心闭环。 |
| 验收场景 | 1 条端到端主流程 ＋ 5 个业务异常/边界场景 ＋ 3 个 AI 相关场景，见第七节。 |
| 应做功能 | 登录与三类角色基础权限、查询筛选、状态变更日志、图片上传与查看、模拟数据初始化、统一异常处理，见第六节。 |
| 选做功能 | 站内提醒、可视化图表、重复报修提示优化、移动端适配，见第六节。 |
| 本期不做 | 见第六节 6.4，含在线支付、即时聊天、身份认证对接、跨校区多租户、图片识别定损、自动派单等。 |
| 完成方式 | 1 人独立完成；可借用 AI 编程工具，但须能独立解释核心模块、数据模型、关键规则、提示词设计与测试方法。 |
| 主要风险 | ① 加 AI 后范围膨胀 → 只做 1 项、设熔断条款（第六节 6.1 末）；② 模型服务不可用或密钥缺失 → Mock 适配器＋规则兜底；③ 状态流转与并发争用（重复改派/重复验收/重复扣状态）→ 状态机约束＋乐观锁＋幂等校验；④ 图片/学生信息泄露 → 权限隔离、脱敏样例、AI 输入不传个人信息；⑤ 时间不足 → 首版限定一个宿舍片区，选做项一律后置。 |

## 二、硬性淘汰条件检查

| # | 淘汰条件 | 判定 | 说明 |
| ---: | --- | --- | --- |
| 1 | 无法说明具体目标用户和使用场景 | 未触发 | 三类用户明确；现有流程已由学生说明，按要求按简化流程建模，不展开细节走访 |
| 2 | 无法形成可演示的核心业务闭环 | 未触发 | 报修→派单→处理→验收/返修闭环完整 |

| 4 | 核心范围明显超出项目周期和个人能力 | 未触发（有条件） | 前提：首版限定一个宿舍片区、6 个必做模块封顶、选做后置、执行熔断条款 |
| 5 | 项目主体只是调用外部 API 或套一个聊天窗口 | 未触发（有条件） | 主体是工单状态流转与业务规则；AI 仅作用于 M2 的辅助填写，不做聊天窗口。若后续把 AI 扩成主体须重新评估 |
| 6 | 依赖真实支付、复杂即时通信、大规模并发、多租户或跨校数据共享 | 未触发（有条件） | 前提：以上均列入"本期不做" |
| 7 | 涉及难以控制的隐私、医疗诊断、金融交易或其他合规风险 | 未触发（有条件） | 使用模拟/脱敏样例；AI 输入仅含故障描述与类别词表，禁传姓名学号 |
| 8 | 依赖难以获得的硬件或设备 | 未触发 | 无需摄像头、门禁、IoT 设备 |

**结论**：无硬性淘汰项，**有条件推荐立项**。成立条件为第 3、4、5、6、7 项的"前提"全部满足。

| 维度 | 分值 | v1 | v2 | 判断依据 |

| 技术可行性 | 15 | 14 | 13 | 技术栈熟悉且常规；AI 服务可用性、密钥管理与输出不确定性新增风险，已用 Mock 与降级部分对冲 |
| 范围与个人工作量 | 20 | 18 | 15 | 6 个必做模块已达个人项目上限，AI 评测与降级需额外工作量，依赖熔断条款保底 |
| 展示与成长价值 | 10 | 8 | 9 | 状态流转、越权拦截、AI 辅助＋评测对比均可现场演示，技术亮点提升 |

## 五、AI 能力设计规格（仅此 1 项）

### 5.1 做什么 / 不做什么

**选定：M6 报修描述智能辅助填写**。学生在 M2 报修页输入一段自然语言故障描述后，点击"智能辅助填写"，系统给出**可修改的草稿**：建议故障类别、紧急程度提示、还需补充的信息。学生确认或改写后才提交。

**为什么选它**：作用点就在主流程入口，不改变工单状态机；输出是可枚举、可校验的结构化字段，容易设计有预期结果的评测样例；模型失效时最易降级。

**未选方向及理由**：

| 候选 | 不选原因 |
| --- | --- |
| 图片识别定损 / 故障图片分类 | 需多模态模型与真实标注图片，依赖强、数据量不足、难评测 |
| AI 自动派单 | 与 M3 的业务规则冲突，派单结果涉及责任归属，模型不可解释且易出错 |
| 维修知识库 RAG 答疑 / AI 客服 | 需另建知识库与检索链路，等于第二个项目，超出个人周期 |
| 智能生成维修方案 | 输出自由度高、无可靠验收标准，且涉及安全责任 |

### 5.2 输入输出规格（编号清单）

| # | 规格 | 内容 |
| ---: | --- | --- |
| S1 | 输入 | 仅 `description`（学生填写的故障描述文本）＋ 系统配置的故障类别词表 ＋ 房间类型。**禁止传入姓名、学号、手机号、图片** |
| S2 | 输出 Schema | JSON：`suggestedCategoryId`（必须是词表中存在的 ID）、`urgency`（枚举 普通/较急/紧急）、`missingInfo`（字符串数组，补充信息提示）、`reason`（不超过 1 句依据） |
| S3 | 服务端强校验 | JSON 可解析、字段齐全、枚举合法、`suggestedCategoryId` 属于当前启用词表、`missingInfo` 长度与文本长度上限；任一不合格判为"生成失败"，不得写入业务字段 |
| S4 | 人工确认 | 模型输出只作为草稿填充表单，**必须学生确认或改写**；不得自动提交、自动定类别生效、自动派单、自动改变工单优先级 |
| S5 | 调用记录 | 记录 `ai_assist_status`、耗时、失败原因、原始输出（脱敏）、学生最终采用的类别与是否改写，供评测与答辩追溯 |
| S6 | 状态枚举 | `未使用` / `生成中` / `已生成待确认` / `已采用` / `已改写` / `生成失败（可重试）` / `已跳过`；失败工单在列表中有明确标识与重试入口 |
| S7 | 超时与重试 | 建议连接/读取超时可配置（如 5s/15s），最多重试 1 次；重试仍失败即进入 S8 降级，不阻塞表单提交 |
| S8 | 降级链 | 模型不可用 → **关键词规则兜底**（类别词表同义词映射给出建议） → 规则也无匹配 → 提示学生手动选择类别。任一路径下报修均可正常提交，M1～M5 不受影响 |
| S9 | 隐私与密钥 | 请求日志脱敏，Key 仅服务端环境变量；Mock 适配器输出与真实接口同 Schema，便于离线回归测试 |
| S10 | 熔断条款 | 中期检查时若模型接入未通过 5.4 评测，允许 M6 以"仅规则模式 ＋ 评测记录 ＋ 原因分析"结题，M1～M5 仍须完整交付，并在论文中如实说明 |

### 5.3 学生自行实现的环节（非模型部分）

1. 提示词模板与类别词表/同义词配置管理；
2. 输出结构校验、枚举与外键校验、异常捕获与超时控制；
3. 关键词规则兜底引擎与 Mock 适配器；
4. 草稿填充、人工确认/改写交互与状态持久化；
5. 评测样例集、评测脚本与指标统计；
6. 调用日志、失败状态、重试与跳过入口。

> 这 6 项是答辩中必须能独立解释的**个人工作量**；模型调用本身不构成项目主体。

### 5.4 评测方案（可验收）

| # | 项目 | 要求 |
| ---: | --- | --- |
| P1 | 评测样例集 | ≥ 12 条描述，每条标注预期类别；覆盖口语化/简称、多故障混合、类别无关或无意义输入、超长文本、空输入 |
| P2 | 指标 | 类别 Top-1 准确率、JSON 结构校验通过率、越界类别拦截率、无依据输入拒答/兜底率、平均耗时 |
| P3 | 对照实验 | 同一评测集分别跑「仅关键词规则」与「规则＋模型」，给出对比表，说明 AI 的实际增益与代价 |
| P4 | 降级验证 | 断开模型服务 / 使用非法 Key / 返回非法 JSON，各跑一次，验证 S6～S8 状态与报修主流程不中断 |
| P5 | 交付物 | 评测样例集、脚本、结果表与分析，连同模型输入输出约束文档一并归档 |

## 六、范围控制（四级功能清单）

### 6.1 必做（6 项，缺一不可形成闭环与 AI 验收）

| # | 模块 | 关键规则与预期结果 | 主要角色 |
| ---: | --- | --- | --- |
| M1 | 宿舍与维修范围配置 | 维护楼栋、楼层、房间、故障类别及同义词；维护维修人员与其负责的类别/楼栋范围；删除已被工单引用的基础数据须拦截或转为停用 | 宿管 |
| M2 | 报修受理 | 学生填写地点、故障类别、描述并上传图片；可查历史工单；**同一房间存在未结同类报修时给出提示并阻止或要求确认**；图片失败可先交文字报修并补传 | 学生 |
| M3 | 派单与改派 | 按故障类别＋负责范围推荐并指派维修人员；记录接单、退单、改派及理由；退单后工单回到待受理状态，不得停留在中间态 | 宿管、维修人员 |
| M4 | 维修与验收 | 维修人员提交处理说明与结果；学生确认完成或提出返修；**每次处理独立留痕，返修生成新一轮处理记录且不覆盖历史**；仅当前受理人可操作对应环节 | 维修人员、学生 |
| M5 | 工单统计 | 按楼栋、故障类别、时间区间统计工单量、平均处理时长、返修次数/返修率；统计口径与状态定义一致 | 宿管 |
| M6 | 报修描述智能辅助 | 按第五节 S1～S10 实现，含结构校验、人工确认、关键词兜底、Mock 适配、调用记录与评测 | 学生（后端代理） |

> **范围封顶**：6 个必做模块已达个人毕设建议上限（4～6 个）。M6 是**唯一**允许的 AI 能力；新增任何 AI 或特色功能前，必须先删减同级范围并重新评分。

### 6.2 应做（保证系统基本完整）

1. 登录与会话管理，学生/宿管/维修人员三类角色的菜单与数据可见范围隔离。
2. 工单列表的查询与筛选（状态、楼栋、类别、时间、我的工单）。
3. 状态变更日志：记录操作人、时间、前后状态与备注，供追溯与答辩演示。
4. 报修图片上传、存储与按权限查看；文件类型、大小校验与失败提示。
5. 初始化/模拟数据脚本：楼栋房间、故障类别及同义词、维修人员、演示账号、若干处于不同状态的工单；**脚本内明确标注"模拟数据"**。
6. 统一异常处理与表单校验：必填项、越权访问、非法状态跳转、重复提交、图片上传失败、AI 超时均有明确提示与可恢复路径。
7. AI 辅助状态在工单详情/列表中的展示、重试与跳过入口。

### 6.3 选做（核心版本跑通后再加，按此顺序）

1. 站内消息/站内信提醒（新工单、派单、待验收）。
2. 统计结果可视化图表（趋势、类别占比）。
3. 重复报修提示的规则优化（时间窗口、类别相似度）。
4. 移动端页面适配，方便学生在宿舍现场提交。

### 6.4 本期不做（主动排除）

1. 在线支付、维修收费、材料计费。
2. 即时聊天、语音通话、复杂消息推送。
3. 对接学校统一身份认证（CAS/OAuth）、短信网关、**校内既有报修系统**的数据同步。
4. 跨校区、多学校、多租户与大规模并发。
5. 图片识别定损、AI 自动派单、维修知识库 RAG、AI 客服聊天、自动生成维修方案。
6. 地图定位、门禁/IoT 设备对接、人脸识别。

> **降级逻辑（总）**：任一选做项或外部依赖受阻，不影响 6.1 必做闭环可运行、可演示。
> ① 图片上传失败 → 文字报修先提交 ＋ 补传入口；② 提醒不可用 → 工单状态与列表承担查询职责；③ 统计异常 → 不影响工单流转；④ **模型不可用/超时/非法输出 → 关键词规则建议 → 学生手选类别，报修照常提交**；⑤ Mock 适配器保证无网络无密钥时评测与答辩可复现。

## 七、验收方案

### 7.1 端到端主流程（答辩演示）

学生 A 在 3 栋 502 输入"洗手池水龙头一直滴水，地上有点积水" → 点"智能辅助填写" → 系统建议类别「给排水-龙头漏水」＋紧急程度＋补充信息提示 → A 确认并上传示意图片后提交 → 宿管受理，按类别与负责范围派单给维修人员 B → B 接单、上门、提交处理说明与结果 → 学生 A 确认验收 → 工单归档 → 宿管在统计页看到该工单处理时长计入。

### 7.2 业务异常与边界场景

| # | 场景 | 期望结果 |
| ---: | --- | --- |
| E1 | 维修人员接单后退单，宿管改派给另一人 | 工单回到待受理，退单理由留痕，改派后仅新受理人可处理，不产生两条并行处理记录 |
| E2 | 学生提出返修 | 工单回到处理中，生成新一轮处理记录，历史处理记录与验收意见完整保留，返修次数计入统计 |
| E3 | 同一房间已存在未结同类报修时再次提交 | 给出明确提示并阻止重复派单（或要求学生确认后关联原工单） |
| E4 | 越权与非法状态跳转（学生执行派单、维修人员自行确认验收、对已归档工单重复验收） | 全部拦截并返回可读提示，状态与数据不被破坏 |
| E5 | 报修图片上传失败 / 文件类型不合法 | 给出明确失败原因，允许文字报修先提交并在后续补传（降级路径） |
| E6 | 并发重复操作（重复点提交、重复点验收、并发改派） | 幂等校验与乐观锁生效，只产生一条工单/一条有效验收记录 |

### 7.3 AI 相关验收场景

| # | 场景 | 期望结果 |
| ---: | --- | --- |
| A1 | 模型返回不在词表中的类别 / 非法 JSON / 字段缺失 | 结构校验判为生成失败，不写入业务字段，进入规则兜底，页面显示失败原因与重试入口 |
| A2 | 断开模型服务 / 使用非法 Key / 请求超时 | 关键词规则给出建议或提示手选，报修主流程完整可提交，`ai_assist_status` 正确记录 |
| A3 | 无关或无意义描述（如"随便写写"） | 不强行归类，给出"信息不足"提示并要求学生手动选择；评测集记录该用例 |
| A4 | 评测集对照实验 | 输出 P1～P5 的指标与「仅规则 vs 规则＋模型」对比结果表 |
