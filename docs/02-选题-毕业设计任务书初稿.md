## 一、论文（设计）的选题意义

高校宿舍报修直接关系学生日常生活。据学生了解，本校报修一般由学生通过校内报修系统提交，后续派单、沟通与结果反馈主要通过电话完成。口头沟通中的接单、退单、返修意见与处理结果不易在系统中留痕，学生查询处理进度不便，处理时长与返修情况需要人工汇总，同一问题也可能被重复登记。

本课题面向学生、宿管/后勤受理员、维修人员三类角色，设计并实现一套高校宿舍报修与维修工单管理系统，把上述环节固化为可追溯的工单状态流转，形成"提交—受理派单—维修处理—学生验收或返修—归档统计"的完整业务闭环，并给出角色权限、状态留痕与统计分析的可运行实现。系统采用 Spring Boot（Java）、MySQL 8 与 Vue 前后端分离架构，另引入一项大模型辅助能力：学生填写自然语言故障描述后生成可修改的结构化草稿，配合服务端校验、人工确认与失败降级，用于探讨 AI 能力在业务系统中"可验收、可降级"的工程化接入方式。

本系统为教学模拟实现，不与校内既有报修系统对接，不采集真实学生信息；楼栋房间、故障类别、维修人员、演示账号与图片均为模拟或脱敏样例。论文应如实说明该定位，不得表述为真实上线效果或实际效率提升，不得引用未经核实的调研数据。

## 二、论文（设计）的任务和基本要求

本系统采用 JDK 21（LTS）、Spring Boot 3.5.x、MySQL 8.0、Vue 3.5.x（Node.js 22 LTS、Vite 6/7、Element Plus 2.x）等资料丰富、便于复现的主流稳定版本。主流程简化为：学生提交报修 → 宿管受理派单 → 维修人员处理 → 学生验收或返修 → 归档统计；状态取"待受理、已派单、处理中、待验收、已完成"五种，返修回到处理中，退单回到待受理，不设多级审批。本系统具有的功能有：

**后台（管理端）**

1. 宿舍与维修范围配置：维护楼栋、房间、故障类别及同义词、维修人员负责范围；已被引用的基础数据转停用而非直接删除。
2. 派单与改派：按故障类别与负责范围指派，记录接单、退单、改派及理由；退单回到待受理，不产生并行处理记录。
3. 工单统计：按楼栋、故障类别、时间统计工单量、平均处理时长与返修率，口径与状态定义一致。
4. 报修描述智能辅助（唯一 AI 能力）：模型输出经服务端 JSON 结构校验，类别须属于启用词表、紧急程度为枚举；仅为草稿，须学生确认或改写后提交，不自动定类别、不自动派单；模型不可用或输出非法时依次降级为关键词规则建议、学生手动选择，报修仍可正常提交；提供离线 Mock 适配器，保证无网络无密钥时可评测与答辩。

**前台（学生端与维修端）**

1. 报修受理：填写地点、类别、描述并上传图片；同一房间未结同类报修提示拦截；图片失败可先交文字报修后补传。
2. 维修与验收：维修人员提交处理说明与结果；学生确认完成或提出返修；每次处理独立留痕，返修不覆盖历史记录。
3. 三类角色登录与权限隔离：菜单与数据可见范围按角色控制，越权与非法状态跳转一律拦截。
4. 工单查询与留痕：按状态、楼栋、类别、时间筛选，记录状态变更日志与 AI 辅助状态（含生成失败可重试、已跳过）。
5. 模拟数据初始化与统一异常处理：提供初始化 SQL、演示账号与异常提示，覆盖重复提交、并发重复验收等边界。

**验收与交付要求**：交付可独立运行的系统、源代码、运行环境说明、模拟数据、部署说明、测试记录与数据库设计；答辩演示一条端到端主流程，并至少测试退单改派、学生返修留痕、重复报修拦截、越权跳转等两个以上异常场景；现场验证 AI 服务异常时的降级链路。AI 能力须提交输入输出约束文档、不少于 12 条带预期结果的评测样例、评测脚本与结果表，并做"仅规则"与"规则＋模型"对照。中期检查若模型接入未通过评测，允许以"仅规则模式＋评测记录＋原因分析"结题，其余模块仍须完整交付。本课题一人一题、独立完成，可用 AI 编程工具辅助，但须能独立解释核心模块、数据模型、状态机、提示词设计与测试方法。
